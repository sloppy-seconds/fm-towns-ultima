# Unsupervised work prompt

Give this to an agent together with `docs/recomp-plan.md`. It exists because a plan says what to do and
this session showed that the failure mode is not doing the wrong thing, it is **doing the right thing and
believing a wrong check**.

## The prompt

> Work `docs/recomp-plan.md` stage by stage, starting at stage 1. Do not start a stage until the previous
> stage's gate passes.
>
> **For every stage, before writing any prose, write the check that would fail if you were wrong.** The
> check goes in `tools/` and runs from `node tools/checkall.js`. Then make it fail on a deliberately wrong
> value, confirm it fails, and only then proceed. A check that has never been seen to fail is a comment.
>
> **Every number in a document is generated by a command, and the command goes in the document.** Not
> recalled, not carried over from an earlier page. If you cannot produce the command, write the number as
> unverified or omit it.
>
> **When a measurement contradicts a page, stop and reconcile before continuing.** Do not append a
> correction beside the old claim and leave both. One of them is wrong and the page has to say which.
>
> **When you find you were wrong, say so in the commit message in the first person.** This session's most
> valuable output was a list of its own corrections. A silent fix looks the same as never having erred.
>
> **Never claim a stage complete on a check you wrote after forming the conclusion.** The order matters:
> check first, conclusion second. If you notice you have it backwards, stop and rewrite the check against
> a case you know the answer to.
>
> **Commit in logical units and run `node tools/checkall.js` before each.** If a check fails, fix it or
> record why it cannot pass. Never commit through a failing gate, and never let a pipeline swallow the
> exit code.
>
> **Stop and write up when a stage's budget is spent, even if it is unfinished.** An honest partial result
> with its limits stated is worth more than a complete-looking one that drifted.
>
> Report at the end of each stage: what was asked, what was done, what was claimed and which command
> proved it, what is outstanding, and what this made stale elsewhere.

## The gates that must exist before stage 1 is finished

These are the ones this session's errors would have been caught by. They do not exist yet and are part of
the work, not a preliminary.

| gate | catches | how it fails |
|---|---|---|
| function boundaries end at a terminator | the era-0 error, where a backwards scan found the previous function | a claimed start whose preceding byte is not `c3`, `c2`, `e9`, `eb`, `90`, `cc`, `00`, `c9 c3` or `8b c0` |
| record offsets assert two knowns | the GEM-is-ANKH error | reading `GEM` without first confirming `maxhp` is 400 and `era` is 2 at the computed offsets |
| a routine's purpose cites its caller's argument | the `0xe0e90`-is-the-roster error | `0xe0e90` called with `\SOUND\ULTIMA.FMB` |
| generated code round-trips | any decoder claim | an emitted function that does not reproduce the input state |

The first three are `verify.js` assertions. The fourth is stage 1's exit condition.

## What this prompt does not fix

It cannot make a wrong *model* of the problem visible. Every check above was written by the same reasoning
that produced the error, and the checks that caught things caught them because they were **external**:
the image bytes, the caller's argument, a real save file.

So prefer external evidence to internal consistency at every opportunity. A check that says "my two
documents agree" is worthless. A check that says "this matches the disc" is not.
