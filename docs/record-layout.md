# The character record layout, solved from the format string

> **MAJOR CORRECTION: the format string is a SAVE format, not a memory layout.** Verified at runtime by
> matching four values the game displays against live memory. `MHP` is in the save file but not in the
> in-memory struct, so **every field from `EXPERIENCE` onward is 4 bytes earlier in memory than this page
> says.** `HP` and everything before it is correct. See [save-vs-memory.md](save-vs-memory.md).
>
> The three anchors this page used to prove the layout (`MAP`, `PLAYER_X`, `PLAYER_Y`) are all *after* the
> omission, so they agreed with each other while being consistently wrong.

Every field offset on this project's map, shrine and formula pages was unnamed, because deriving
roster-field to memory-offset had failed twice. It is now solved, and it changes what several
earlier pages mean.

## The method

The `printf` format string in `ENCHANT.EXP` names every roster field in serialisation order with its
conversion. Reading it from `LINGUAL=%d` to `GATE_TIME=%d` gives **90 field specifications**.

Building a layout from them, `%c` as one byte and `%d` as four:

```
base + running offset, in format order
```

Then anchoring: `0xcdf57` is known from `0xf22f0` to hold a value compared against 3, and `0xcdf6b`
and `0xcdf6f` are known to be used as `y*64 + x`, which is `PLAYER_X` and `PLAYER_Y`.

**The first attempt used `MAP_X` as the anchor and produced contradictions.** It matched at
`0xcdf57` and then drifted 4 bytes by `PLAYER_X`. Swapping the anchor to **`MAP`**, one field earlier,
made three anchors agree exactly:

| address | field | implied base |
|---|---|---|
| `0xcdf57` | `MAP` | `0xcde54` |
| `0xcdf6b` | `PLAYER_X` | `0xcde54` |
| `0xcdf6f` | `PLAYER_Y` | `0xcde54` |

**Record base `0xcde54`, size 339 bytes in format order.** Three independent anchors landing on the
same base is the proof; one would have been a fit.

## What this corrects

**[shrine-function.md](shrine-function.md) named the wrong things.** That page said the shrines
grant stats. They do not:

| shrine branch | address | field, now named |
|---|---|---|
| `0x60` | `0xcde95` | **`GOLD`**, `+= 2` |
| `0xfc` | `0xcde9d` | **`ERA`**, `+= 1` |
| `0xf0` | `0xcde5e` | **`SPID`**, `+= 1..4` |
| `0xf8` A | `0xcdeeb` | **`RING`**, `+= 1` |
| `0xf8` B | `0xcdeef` | **`WAND`**, `+= 1` |

**Two of these are startling and one is almost certainly a bug in the game.**

`0xf8` grants a **`RING`** or a **`WAND`**, which are inventory items and not stats. The earlier page called
those "a stat" and could not name them because of the glyph problem. The glyph problem was not the
obstacle; the field mapping was.

`0xf0` grants **`SPID`**. `SPID` is the monster/NPC shape index, and it was established long before
this page that `SPID = profession_index * 4 + 2`. **A shrine that increments `SPID` changes the
character's sprite.** That is either a deliberate polymorph or a bug, and it is not what a shrine
should do.

`0xfc` grants **`ERA`**. Incrementing era is a time-travel effect, not a stat increase.

**So the "shrine" function is misnamed.** It is a tile-triggered effect dispatcher whose four
branches grant gold, era, sprite-id and inventory items respectively. No branch grants a stat.

## The 99 and 999 caps, reinterpreted

The `0x60` branch adds 2 to `GOLD` and clamps at **99** (`0x63`). `maxed_four.hdm` holds
`GOLD=9999`, and the other two references to `0xcde95` at `0xea4b7` and `0xedb58` are plain stores
with no cap.

So **99 is a cap local to this branch**, not a property of `GOLD`. The earlier claim that
"stats clamp at 99, gold at 999" was a reading artifact: the cap belongs to the code path, not the
field.

The `0xf0` branch clamps `SPID` at **999** (`0x3e7`), which for a sprite index is not a meaningful
limit either. Both caps look like defensive bounds rather than game rules.

## The `0xf8` array is the inventory

`[edx + esi*4 + 0xcdee7]` with `esi` from `randMod(14)` is not a "six-element stat array" as
[shrine-function.md](shrine-function.md) guessed. It is the **item inventory**, fifteen consecutive
`%d` fields from `QUICK_SWORD` at `0xcdee7` to `STRANGE_COIN` at `0xcdf1f`.

That resolves the anomaly recorded there, where a roll of 0 to 14 indexed an array the page assumed
was six long. **The array is fifteen entries and the roll is correctly bounded.** There was never an
over-index.

## Why this was hard, stated plainly

Two earlier attempts failed and both failures are instructive:

- **Fixed 4-byte stride from an arbitrary anchor.** Produced half-integer field indices, which
  should have been read as "the model is wrong" rather than "the base is wrong".
- **Anchoring on the wrong field.** `MAP` and `MAP_X` are adjacent and both plausible at `0xcdf57`.
  Choosing the wrong one gave a consistent-looking layout that drifted by exactly one field,
  which is the most convincing kind of wrong answer.

The thing that made it work was **requiring three independent anchors to agree** rather than
accepting one fit.

## What this unblocks

Every page that recorded an unnamed field offset can now name it. That includes the `randMod`
functions still unread: their formulas can be read and written down in field names from the start,
rather than needing a second pass.

**The glyph mapping was never the blocker for this.** That was a wrong diagnosis on
[shrine-function.md](shrine-function.md), and it is worth noting because it directed effort at the
font for several sessions.
