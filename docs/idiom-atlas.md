# The forward idiom atlas: what High C 1.73 emits, and what it never emits

Plan item [0a](plan-attribution.md). This is the gate on the whole preservation track: `hand-asm-positive`
cannot be earned without a list of things the compiler does not do, and item 12b is blocked on this page
existing.

Everything here is the output of compiling a corpus of small C sources with the real FM Towns High C 1.73 kit
and disassembling what came back. Nothing is asserted because it is a plausible thing for a 1990 compiler to
do, and nothing here was inferred from a compile-and-diff mismatch, which is the error this atlas exists to
make impossible.

**Corpus breadth.** 37 probes, 3 distinct frame shapes (frame or not, callee-saved spill, argument base
register), 31 distinct mnemonic sets, 36 distinct instructions emitted in total. The item's failure case is a
corpus that collapses to one shape, which would show the corpus was too narrow rather than the compiler
uniform, and these counts are how that is distinguished rather than asserted.

## The route, and the five constraints that had to be measured

The generator is `Q:\HC386\BIN\HC386.EXE`, the driver, reached by booting the TownsOS hard disk image with the
SDK CD seated. That is the route `highc-authentic-toolchain.md` proved reproduces seven routines byte for
byte. The real-mode `HCD386.EXE` route that `tools/cserve.js` drives was deliberately not used: its optimiser
never engages, so an atlas built on it would record the route's limits as the compiler's.

`tools/atlas-build.py` encodes what that DOS actually allows, and each of these cost a run to find:

| constraint | symptom | consequence for the harness |
|---|---|---|
| the CD wins the boot | the hard image's `AUTOEXEC.BAT` never runs | one command has to be typed, and patching the HDD boot file changes nothing |
| no redirection | `Sorry, redirection and pipe are not supported yet.` | no log file and no progress marker from inside the guest, so completion is watched from the host |
| 8.3 filenames | `A04_PARAMS8.C` answers `file not found` | probe stems are three characters, `A01` to `A32` |
| the driver leaks file handles | eighth compile: `too many files are open` | six compiles per boot, then a reset, so the corpus runs in five chunks |
| the code segment is not always at `0x200` | probes with file-scope data decoded as a run of `add byte ptr [eax], al` | the extent and offset come from the linker map, not from a constant |

The last one is worth stating plainly because it produced confident nonsense rather than an error. `A20`
declares `int m[16][16]`, which puts a 1,024-byte DATA segment ahead of the code in the group, so its code
starts at group offset `0x400`. Reading from `0x200` returned zeros, and Capstone disassembled those zeros into
twenty instructions of plausible-looking x86. The map states the offset, and using it is what turned that
probe from a false reading into the stride-arithmetic evidence it was written to be.

Function extents come from the map's `Segment map` line for the module's `CGROUP CODE` segment, so a probe's
byte count is asserted by the linker rather than inferred by scanning for a `ret`. That is the same standard
item 12a will require of game routines.

## Never emitted across the whole corpus

This is the list that carries the weight. Each entry is an idiom a reader might reasonably expect in this
toolchain's output, stated as the predicate that would have found it, and each is absent over all 32 probes.

- `xor reg,reg` for zeroing
- `mov reg,0` for zeroing
- `test reg,reg` as a zero test
- a `cdq`/`sub`/`sar 1` halving chain produced from a division by a power of two
- a magic-multiply reciprocal for constant division
- `imul` for a small constant multiply
- `rep movsb` or any string op for a byte copy
- `sub esp,N` to allocate locals
- struct padding to a natural alignment
- the `enter` instruction for a frame
- `int 21h` emitted from C

And the positive side, each present somewhere: `sub reg,reg` for zeroing, `cmp` against zero, **`test` with a
memory operand when a mask is used only for its flags**, `sar 1` from a source that halves explicitly,
`cdq`/`and`/`add`/`sar` bias-then-shift, hardware `idiv` even for a constant divisor, `shl` for a stride,
`lea` for a small constant multiply, a manual byte loop rather than a string op, `push reg` to allocate a
local, `setcc` for a relational value, an inline jump table for a dense switch, a compare chain for a sparse
one, `movsx` and `movzx`, `leave` for an epilogue, and `xchg` to move a second result into `eax`.

> **Correction, made in this same session, and it is the most useful thing on the page.** An earlier draft
> said `test` does not appear anywhere in the corpus. That was measured over 32 probes, and none of the 32
> asked the question. A34, `if ((a & b) == 0)`, compiles to
> `test dword ptr [esp + 8], eax; jne`. So the compiler emits `test` quite happily, and the absence in the
> first 32 was an absence of the source shape rather than of the instruction.
>
> This matters because the clustering pass counted 43 game functions using `test` and the obvious move was to
> call that positive evidence of exclusion under the never-emits list. It is not, and the three extra probes
> are what said so. A never-emits entry is only as wide as the corpus that produced it, and the entry that
> survived is the narrower one: `test reg,reg` as a zero test is absent, `test` is not.

## The findings that change how game code should be read

**Zeroing is `sub reg,reg`, never `xor reg,reg`.** `int z; z = 0;` compiles to `sub ecx, ecx` (A08), a zero
return value is `sub eax, eax` (A09), unsigned division zeroes the remainder register the same way with
`sub edx, edx` before `div` (A13), and the spelling most likely to provoke an exclusive-or, `a ^= a`, still
comes out `sub eax, eax` (A33). `xor` does appear when it means something (A35's `s ^ a[i]`), which is what
makes the zeroing claim precise rather than absolute. This matters because the image-wide concentration of
`xor` against `sub` was the signal `docs/compiler-generation.md` used, and a site zeroing with `xor` is now
supported by positive evidence of exclusion rather than an impression.

**A zero test has three distinct shapes and the atlas now names all three.** Testing a *memory operand* against
zero is `cmp x, 0` (A09, A36). Testing a *register* for truthiness is `and reg, reg` (A37: `while (p)` becomes
`and edi, edi; je`). Testing a *mask* is `test mem, reg` (A34: `(a & b) == 0` becomes
`test dword ptr [esp + 8], eax`). What never appears is `test reg, reg`.

This closed a gap the clustering pass found. 220 game functions, a fifth of the module, use `and reg,reg` as a
test, and at the time the atlas had no probe that produced it, which made it look like an unexplained shape. A37
shows it is simply what this compiler does with a register condition. A gap named and then probed is worth more
than a pattern that was never noticed.

**Constant division uses the hardware divide.** `a / 7` becomes `cdq; mov ecx, 7; idiv ecx` (A12). There is no
reciprocal multiply anywhere in the corpus. This is the sharpest single discriminator the atlas has produced,
because it is exactly what v2.31 does instead, and it is why `highc-negative-result.md` ruled 2.31 out.

**Division by a power of two is a bias-then-shift with a single wide shift.** `a / 8` is
`cdq; and edx, 7; add eax, edx; sar eax, 3` (A11), and `(a - 6) / 8` is
`sub eax, 6; cdq; and edx, 7; add eax, edx; sar eax, 3` (A31).

> **Correction to a known-good row.** `AGENTS.md` states that High C 1.73 emits the game's naive `sar`/`sub`
> halving chain. Measured on the exact expression `highc-negative-result.md` quotes from `0xe6a58`, it does
> not: 1.73 produces one `sar eax, 3`, not three `sar 1`. The chain is reachable, but only from a source that
> halves explicitly three times, which A32 confirms emits `sar ecx, 1` three times. So a `sar 1` chain in the
> game is evidence that the game's C said `>>= 1` three times, and is not evidence against 1.73 either way.
> The `idiv` half of that row is confirmed by A10 and A12.

**Structs are packed to byte alignment by default.** `struct P { char c; int i; char d; }` puts `i` at offset
1 and `d` at offset 5, and `sizeof` returns 6 (A25). There is no padding to a four-byte boundary. Every struct
decode in this project should assume byte packing unless a probe says otherwise, because the opposite
assumption moves every field after the first `char`.

**The argument base register follows the frame decision.** Unframed functions read parameters as
`[esp + 4]`, `[esp + 8]` and onward, and framed ones read `[ebp + 8]`. A04 shows eight parameters all reached
through `esp` with no frame at all. This is the `Remove_BP` behaviour that
`docs/highc-authentic-toolchain.md` named, now confirmed across the whole corpus rather than one routine.

**Locals are allocated with `push`, not `sub esp,N`.** An address-taken local becomes `push eax` and then
`[ebp - 4]` (A03). `sub esp,N` for locals never appears. A game routine that does `sub esp, 8` is therefore
not this compiler's answer to a simple local.

**Register allocation is aggressive and the named local often vanishes.** `int t; t = a + b; return t * 2;`
compiles to `mov ecx,[esp+4]; add ecx,[esp+8]; lea eax,[ecx+ecx]; ret`, twelve bytes, no frame, and `t` does
not exist in the output (A02). `lea eax,[ecx+ecx]` is strength reduction on the multiply.

**Constant multiplies are `lea`, and strides are `shl`.** `a*3`, `a*5`, `a*9` become
`lea eax,[ecx+ecx*2]`, `lea edx,[ecx+ecx*4]`, `lea eax,[ecx+ecx*8]` (A22). A 64-byte row stride becomes
`shl eax, 6` (A20). `imul` appears only for a runtime operand (A06).

**Dense switches get an inline jump table.** A15's `switch` over 0..5 emits
`cmp edx, 5; ja ...; jmp dword ptr cs:[edx*4 + 0x11]` with the table immediately following the jump, inside
the function's own bytes (A15, 88 bytes). Sparse switches get a compare chain (A16). A jump table whose target
list sits inside the function body is a shape worth knowing before reading the game's dispatchers.

**Narrow loads use `movsx` and `movzx` as signedness dictates.** A21 reads `signed char` with `movsx`,
`short` with `movsx`, `unsigned char` with `movzx` and `unsigned short` with `movzx`, in field order.

**A relational value can go either way, and the two look nothing alike.** `return a < b;` is
`cmp; setl al; movzx eax, al` (A28), while `if (a == 0) return 1; return 0;` is a branch pair with `mov eax,1`
and `sub eax,eax` (A09).

**`xchg` is used to move a second result into `eax`.** `a % b` is `idiv` then `xchg edx, eax` (A14), and the
same trick appears in A21 and A29. A byte-swap-looking `xchg` in game code may be a value placement, not an
arithmetic operation.

**Byte copies are manual loops.** A30's `while (n-- > 0) *d++ = *src++;` compiles to a `dec`/`jl` loop with
byte loads and stores. No `rep movsb` appears anywhere, which means the compiler does not reach for string ops
and a `rep movsb` in the game is either inline asm or a library routine.

**Globals are linker-supplied absolutes.** `add dword ptr [0x10], eax` (A05) and `add dword ptr [0], eax`
(A24) are relocation sites, which is the class `docs/highc-authentic-toolchain.md` used to reclassify
`0xe1bf4` and `0xe1c24` as base-fold.

## What this does not settle

The atlas describes the compiler. It does not say which of the game's 818 functions this compiler built, and
that is item 0c's job, which is now unblocked. It also does not decide whether the `enter` region is an older
MetaWare library, a different compiler, or hand-written assembly. What it supplies is the lever: a site
containing one of the eleven never-emitted idioms above has positive evidence of exclusion, which is the only
thing that can earn `hand-asm-positive`.

## Reproducing

```
./tools/decode-setup.sh            # capstone, once
./tools/atlas-build.py             # ~20 min: seven boots, 37 probes
./tools/atlas-report.py            # the table and both lists
```

`atlas-build.py` needs `saves/hc.img`, `saves/hc.ccd`, `saves/scratch-tos11en.h0` and `saves/CMOS.BIN`, and
works on a copy of the hard image under `/var/tmp/atlas/`. It never writes to the pristine images.
